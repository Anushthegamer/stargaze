# Master Plan — Stargaze

Standing rules for future work in this repo. Optimized for: correctness on
the first pass, minimal back-and-forth, minimal tokens burned re-debugging.

## 1. TDD for sensor math and celestial calculations

Any change touching `packages/core/src/{coords,planets,moon,orientation,
projection,declination,angles,time}.ts` follows this order, no exceptions:

1. Write/extend the failing test in `packages/core/test/` first.
2. Prefer real reference data (JPL Horizons, IGRF, HYG) over hand-picked
   expected values — see `packages/core/test/fixtures.ts` and
   `test/fixtures/horizons.json` for the existing pattern.
3. Run `npm run test --workspace @stargaze/core` and see it fail for the
   right reason.
4. Implement the minimum to pass.
5. Run the full suite before calling the change done — a regression here is
   an app that points at the wrong star, which is the whole product.

## 2. Mock Sensor Mode for local UI debugging

Never guess at device orientation/GPS/camera behavior from reading code —
verify it. Before debugging any UI/render issue that depends on live sensor
input:

- Use or build a mock sensor path that feeds `OrientationSource`
  (`packages/web/src/sensors.ts`) synthetic alpha/beta/gamma + a fixed
  lat/lon, so the sky view is reproducible without a physical device or a
  USB-tethered phone.
- Mock mode must be explicit and visible (e.g. a query param or dev-only
  toggle), never silently substituted for real sensors in a build that could
  reach a device.
- If no mock path exists yet for the thing being debugged, build the
  smallest one needed before touching render/UI code — don't iterate blind
  against guessed sensor values.

## 3. Keep datasets out of source

Star/constellation/planet/declination catalogs live in
`packages/web/public/data/*.json`, generated by `tools/build_*.py` from
upstream sources (see `NOTICE.md` for licensing). This stays true going
forward:

- No catalog data, star tables, or generated numeric blobs get inlined into
  `.ts`/`.js` source files.
- New data sources get a `tools/build_*.py` generator + a `public/data/*.json`
  output, following the existing pattern in `tools/build_all.py`.
- Source files reference data by loading the JSON at runtime
  (`packages/web/src/data.ts`), never by embedding it.

## 4. Sketch before coding

For anything non-trivial (new math, new data flow, new UI state), write a
short step-by-step plan of the logic — inputs, transforms, outputs, edge
cases — before writing implementation code. Catch a wrong approach in three
lines of plan, not in a half-finished diff.

## Stack reference (so this doesn't get re-derived every session)

- Core: TypeScript, zero runtime deps, pure functions only (`packages/core`)
- Web client: TypeScript + Vite, no UI framework (`packages/web`)
- Mobile: Capacitor 8, Android only (`android/`)
- Server: Express, dev-only HTTPS (`server/`)
- Data tooling: Python 3, stdlib only (`tools/`)
- Package manager: npm workspaces
- Tests: Vitest, verified against JPL Horizons / IGRF reference data

## Deliberately not doing

- Not adding a matrix/AR library (`gl-matrix`, `three.js`) unless the
  renderer moves to WebGL — the current 2D canvas projection doesn't need
  one, and the sensor fusion is already done by the OS before it reaches
  `DeviceOrientationEvent`.
- Not adding a JS-side AHRS/sensor-fusion library — redundant with the
  OS-level fusion already feeding `sensors.ts`.
